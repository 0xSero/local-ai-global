PROJECT / LOCAL AI GLOBAL

One graph from hardware to a working local model.

Local AI Global turns detected hardware into a small set of compatible model artifacts and validated runtime recipes. Every answer stays traceable to normalized records, source links, launch contracts, prices, and measured speed.

01 / SYSTEM FLOW

Discovery is progressive.

User hardware→Registry match→Model choice→Recipe→Local runtime→Evidence

The index carries compact discovery rows. Full model, artifact, hardware, recipe, price, and sweep bodies are opened only when requested. Consumers never flatten the graph into their own database.

READ PATH

Hardware ID → compatible recipes → selected model instance → immutable launch contract → measured evidence.

WRITE PATH

Source material → submission harness → normalized candidate → validation → registry-only review → merge.

Each surface does one job.

Deterministic reads and recursive record resolution. It owns the canonical schemas and never calls providers or starts runtimes.

CLIlocal hardware → selected recipe

Detects the machine, shows compatible models in a TUI, resolves the selected recipe, and performs explicit local actions.

Omarchy plugindesktop UI → CLI and local endpoint

Adds Omarchy-native discovery, lifecycle controls, and agent configuration without creating an Omarchy-specific copy of registry data.

Submission harnesssource evidence → reviewable JSON diff

Imports, normalizes, validates, and stages additions. It is the only path allowed to propose changes to the registry tree.

04 / SOURCE OF TRUTH

The registry is a recursive tree.

index.json
└── recipe/<id>.json
    ├── model_instance_id → model-instance/<id>.json
    │   └── model_id      → model/<id>.json
    ├── hardware_id       → hardware/<id>.json
    └── speed_sweeps_ids  → speed-sweeps/<id>.json

price/<product>/<region>.json
└── hardware[].id         → hardware/<id>.json

Registry IDs are stable machine keys. Human interfaces resolve them into model names, hardware names, publishers, engines, memory, storage size, dates, and measured rates. Raw IDs remain available in record detail and JSON.

hardware

A distinct accelerator and memory configuration.

model

The canonical model family and publisher identity.

model-instance

An exact downloadable artifact, quantization, or fine-tune.

recipe

One artifact, hardware target, engine, topology, and launch contract.

speed-sweeps

Measured performance evidence attached to a recipe.

price

A regional market observation with currency, condition, source, and time.

05 / HUGGING FACE

Provider data enriches the graph. It does not own it.

  • Each model instance supplies its authoritative Hugging Face URL.
  • Public model-card metadata, publisher identity, repository storage, license, downloads, and likes resolve from that URL.
  • A user connection adds identity and gated-repository access without storing the token in registry JSON.
  • The CLI may inspect the local Hugging Face cache and download a selected artifact after explicit user action.
  • Remote failure degrades to normalized registry metadata; recipe resolution still works offline.

07 / DATA SOURCES

Discovery is not validation.

The signed-in local.ai/api/search/catalog endpoint enumerates model and hardware routes. Full Quick Start evidence lives on the model pages, while bulk measured data enters through a read-only Postgres publication. Both paths create candidates until an immutable launch and real completion pass acceptance.
